## Повар, на котором держится страница

Представьте ресторан, где на кухне всего один повар. Он готовит все блюда, принимает новые заказы и выносит готовое в зал. Делать два дела одновременно он не умеет: пока режет лук, всё остальное ждёт.

Браузер устроен точно так же. На каждой вкладке есть [главный поток](term:main-thread), и это и есть наш повар. В нём выполняется весь ваш JavaScript, обрабатываются клики и прокрутка, считаются стили и рисуется страница. Одно за другим, никогда не вместе.

А чтобы повар не запутался, у него есть простой распорядок дня. Он повторяется по кругу, пока открыта вкладка, и называется циклом событий:

![Цикл событий: одна задача, все микрозадачи, и если пора, кадр](/images/event-loop.svg)

Выглядит просто, но в каждом шаге есть свои правила. Разберём их по очереди, начиная с самого обычного.

## Задачи: заказы по одному

[Задачей](term:task) называют любой кусок работы, который приходит снаружи: клик пользователя, срабатывание таймера, ответ от сервера, загрузка скрипта. Всё это складывается в очередь, как заказы на кухне.

Правило первое и главное: повар берёт из очереди один заказ и доводит его до конца. Пока ваша функция выполняется, браузер не прервёт её ради клика, таймера или отрисовки. Это называют выполнением до конца (run to completion).

У этого правила есть обратная сторона. Если одна задача длится долго, повар занят, и страница замирает целиком: кнопки не нажимаются, текст не выделяется, анимации на JavaScript стоят. Попробуйте сами:

<div data-demo="block"></div>

Обратите внимание на синий кружок. Его крутит CSS-анимация, а такие анимации браузер умеет вести в отдельном потоке, на [композиторе](term:compositor). Поэтому он продолжает вращаться, даже когда повар занят. Подробнее про это было в [гайдлайне про анимации](/posts/perf-120fps/).

Отсюда первый практический вывод: тяжёлую работу надо резать на куски. Если между кусками отдавать управление, например через `setTimeout`, повар успеет между ними принять клик и нарисовать кадр.

## Отрисовка: подача блюд по звонку

Посетители видят только то, что повар вынес в зал. В браузере это отрисовка: пересчитать стили, разложить элементы по местам, нарисовать пиксели. Но повар выносит блюда не после каждого заказа, а когда звенит звонок.

Звонок здесь играет роль [vsync](term:vsync): это сигнал от экрана, что он готов показать новый кадр. Экран 60 Гц звонит 60 раз в секунду, экран 120 Гц вдвое чаще. Если звонок прозвенел, а повар как раз закончил задачу, он идёт рисовать кадр. Если звонка не было, берёт следующий заказ.

Из этого следует неожиданная вещь. Раз отрисовка случается только между задачами, всё, что вы поменяли внутри одной задачи, браузер видит одним итоговым снимком. Вот этот код ничего не покажет:

```js
box.style.display = 'none';
box.style.display = 'block';
```

Элемент не мигнёт, потому что между этими строчками не было кадра. Браузер увидит только финальное `block`.

### requestAnimationFrame: последний шанс перед подачей

Иногда нужно сделать что-то ровно перед тем, как блюдо уйдёт в зал. Для этого есть `requestAnimationFrame`. Колбэк, переданный в него, браузер выполнит прямо перед расчётом стилей и отрисовкой следующего кадра.

Поэтому для анимаций на JavaScript нужен именно он, а не `setTimeout`. Таймер ничего не знает про звонок: он может сработать два раза за один кадр и сделать лишнюю работу, а может пропустить кадр, и анимация дёрнется. `requestAnimationFrame` срабатывает ровно один раз на кадр.

Есть одна тонкость. Если внутри колбэка `requestAnimationFrame` попросить ещё один, новый колбэк не выполнится в этом же кадре, он подождёт следующего звонка. Иначе цикл анимации никогда бы не закончился.

### Почему CSS-переход не перезапускается

На этой тонкости спотыкаются все. Допустим, квадрат уже доехал вправо, и мы хотим запустить анимацию заново: вернуть его влево без перехода, а потом плавно отправить вправо. Интуитивный код выглядит так:

```js
box.style.transition = 'none';
box.style.transform = 'translateX(0)';
box.style.transition = '';
box.style.transform = 'translateX(300px)';
```

И он не работает. Всё происходит внутри одной задачи, браузер видит только итог «квадрат справа, переход включён», а квадрат и так был справа. Двигаться некуда. Сравните три способа:

<div data-demo="transition"></div>

Первый способ ничего не делает. Второй ждёт, пока браузер нарисует кадр с квадратом слева, и только потом отправляет его вправо. Для этого нужно два `requestAnimationFrame` подряд: первый срабатывает ещё до отрисовки нужного кадра, а второй уже после неё. Третий способ просит браузер посчитать стили прямо сейчас, через чтение `getComputedStyle`. Он тоже работает, но это тот самый [принудительный reflow](term:reflow), который в больших количествах тормозит страницу.

## Микрозадачи: срочные дела, которые нельзя отложить

Осталось последнее правило, самое хитрое. Кроме обычных заказов у повара бывают срочные дела: «как закончишь резать, сразу посоли». Это [микрозадачи](term:microtask). Их создают `Promise.then`, `await`, `queueMicrotask` и `MutationObserver`.

У микрозадач два важных свойства.

Первое: их выполняют сразу, как только опустел [стек вызовов](term:call-stack), то есть как только закончился текущий кусок JavaScript. Не через задачу и не через кадр, а прямо сейчас, до всего остального. Поэтому код после `await` продолжается почти сразу.

Второе: повар разбирает срочные дела до конца, включая те, что появились, пока он их разбирал. Если каждая микрозадача ставит новую, повар никогда не освободится, и страница зависнет точно так же, как от бесконечного цикла:

```js
// зависнет: каждая микрозадача ставит следующую, очередь не кончается
function loop() {
  Promise.resolve().then(loop);
}
loop();

// не зависнет: каждый вызов становится отдельной задачей,
// и между ними браузер успевает рисовать и отвечать на клики
function loop2() {
  setTimeout(loop2, 0);
}
loop2();
```

## Загадка с кликом

Напоследок мой любимый пример из доклада Джейка. Он отлично проверяет, насколько хорошо вы поняли микрозадачи. На кнопке висят два обработчика клика, и каждый ставит микрозадачу:

```js
button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('Микрозадача 1'));
  console.log('Обработчик 1');
});
button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('Микрозадача 2'));
  console.log('Обработчик 2');
});
```

Если нажать на кнопку мышкой, порядок будет такой: обработчик 1, микрозадача 1, обработчик 2, микрозадача 2. Браузер сам вызывает обработчики один за другим. После первого стек пустеет, и повар сразу разбирает его срочное дело.

А если вызвать `button.click()` из кода, порядок другой: оба обработчика, а потом обе микрозадачи. Обработчики вызываются изнутри вашего скрипта, и пока он не закончился, стек не пустеет. Срочным делам приходится ждать. Проверьте оба способа:

## Подведём итоги

Весь event loop помещается в несколько правил:

1. У страницы один [главный поток](term:main-thread), и он делает всё по очереди.
2. Задачи выполняются по одной и до конца. Долгая задача замораживает страницу.
3. Отрисовка происходит только между задачами и только когда подошло время кадра. Всё, что вы поменяли внутри одной задачи, браузер видит одним снимком.
4. `requestAnimationFrame` срабатывает ровно один раз перед каждым кадром, и анимации на JavaScript нужно делать на нём.
5. Микрозадачи выполняются сразу, как опустеет стек, и всегда до конца очереди.

Если хочется копнуть глубже, посмотрите доклад Джейка целиком: там больше примеров и очень наглядные анимации. А в [гайдлайне про анимации](/posts/perf-120fps/) эти правила превращаются в практику: как не терять кадры на 120 Гц.
