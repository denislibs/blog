Привет, друзья!

За годы работы фронтенд-разработчиком я повидал разный код. Лапшу на тысячу строк, функции с десятью флагами, классы-боги, которые знают обо всём на свете. Но то, что люди делают с помощью `useEffect`, это отдельный жанр ужасов.

Вы наверняка тоже встречали такое. Огромный компонент. В нём пять эффектов, каждый на полсотни строк. Список зависимостей на пол-экрана, а над ним стыдливое `// eslint-disable-next-line`. Один эффект меняет состояние, на это срабатывает второй, тот меняет ещё что-то, и просыпается третий. Чтобы понять, почему на экране появилось число 42, надо мысленно прогнать всю цепочку, как программу на goto. А иногда цепочка замыкается сама на себя, и вкладка браузера тихо умирает от бесконечного цикла.

Выглядит это примерно так. Пример собирательный, но каждую строчку я видел в настоящих проектах:

```tsx
function Checkout({ cart, user, onTotalChange }) {
  const [items, setItems] = useState([]);
  const [total, setTotal] = useState(0);
  const [discount, setDiscount] = useState(0);
  const [isValid, setIsValid] = useState(false);

  useEffect(() => {
    setItems(cart.items.filter((i) => i.available));
  }, [cart]);

  useEffect(() => {
    setTotal(items.reduce((sum, i) => sum + i.price * i.count, 0));
  }, [items]);

  useEffect(() => {
    setDiscount(user.isVip ? total * 0.1 : 0);
  }, [user, total]);

  useEffect(() => {
    setIsValid(items.length > 0 && total - discount > 0);
    onTotalChange(total - discount);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [items, total, discount]);

  // …ещё 300 строк
}
```

Четыре эффекта, четыре лишних рендера, функция `onTotalChange`, которая вызывается неизвестно когда, и отключённый линтер. А ведь всё это одна строчка арифметики.

У этого стиля даже есть название. Евгений Паромов в своём [видео про антипаттерны React](https://www.youtube.com/watch?v=b2o-iJzAfTc) называет его useEffect driven development: разработка, где вся логика держится на цепочках эффектов. И считает одним из самых злобных антипаттернов современного React. Я с ним полностью согласен.

Давайте наконец разберёмся, когда `useEffect` нужен, а когда нет. Спойлер: почти никогда.

## Главное правило

Документация React называет эффекты запасным выходом из модели React. Они нужны, чтобы синхронизировать компонент с чем-то внешним: с виджетом, который написан не на React, с сетью, с API браузера.

Отсюда простой тест. Перед тем как написать `useEffect`, задайте себе вопрос: с какой внешней системой я синхронизируюсь? Если ответ «ни с какой», эффект не нужен. Всё, можно дальше не читать.

И второй тест, ещё проще, его хорошо формулирует Паромов: посмотрите, что лежит внутри эффекта. Если там нет ничего, кроме `setState`, эффект написан неправильно. Любую такую логику можно переписать без него.

Но раз уж вы здесь, давайте разберём, почему эффекты так плохи там, где они не нужны, и чем их заменить.

## Почему лишний эффект это дорого

Вспомним, как React показывает изменения. Сначала он вызывает ваши компоненты и считает, что поменялось. Это рендер. Потом применяет изменения к DOM, это называют коммитом. Потом браузер рисует кадр. И только после этого, обычно уже после отрисовки, запускаются эффекты. Подробно про этот порядок я писал в статьях [про event loop](/posts/event-loop/) и [про то, как рендерят фреймворки](/posts/render-timing/).

Теперь представьте эффект, который просто вычисляет значение и кладёт его в состояние. Получается такая последовательность:

1. React рендерит компонент со старым значением.
2. Применяет изменения к DOM, и браузер может успеть нарисовать устаревший кадр.
3. Запускается эффект и вызывает `setState`.
4. React рендерит компонент ещё раз, теперь с правильным значением.

Два рендера вместо одного, и в промежутке на экране может мелькнуть неправильное число. А если эффекты зависят друг от друга, рендеров становится столько, сколько звеньев в цепочке. Нажмите кнопку и сравните:

## Корень проблемы: одна правда в двух местах

Лишние рендеры это неприятно, но это симптом. Настоящая болезнь глубже. Каждый раз, когда эффект ставит одно состояние на основе другого, у вас появляются две копии одной и той же информации. Полная сумма корзины лежит и в товарах, и в отдельном `total`. Выбранный пользователь лежит и в списке, и в `selectedUser`.

А раз копий две, их надо постоянно синхронизировать. `useEffect` для этого плохой инструмент: это не настоящая реактивность, а просто способ вызвать `setState`, когда что-то поменялось. Синхронизация получается в одну сторону и с задержкой на рендер. Стоит кому-то поменять `total` напрямую, мимо эффекта, и копии разъезжаются. Так и появляются баги вида «в шапке одна сумма, а в корзине другая».

Принцип, который это лечит, называется единым источником истины (single source of truth). У каждого факта должно быть ровно одно место, где он хранится. Паромов называет свой подход разделением источника истины и кеша, а я бы сформулировал его так:

- в состоянии храним только исходные факты, которые нельзя ниоткуда вычислить: что ввёл пользователь, что выбрано, какой открыт таб;
- всё, что можно вычислить из фактов, вычисляем при рендере и нигде не храним;
- данные с сервера это кеш, а не состояние, и им управляет библиотека запросов, а не ваши эффекты.

Если держаться этих трёх правил, большинству эффектов просто нечего делать. Синхронизировать нечего, потому что копий нет.

## Код, который читается как goto

Есть и ещё одна проблема, которую сложно объяснить джуну, но хорошо понимает каждый, кто дебажил такой код. Его невозможно читать сверху вниз.

Вы видите клик, который меняет `selectedCell`. Идёте искать, кто его использует, и находите эффект выше по файлу. Он меняет `formData`. Ищете, кто использует `formData`, и находите ещё один эффект ниже. Тот меняет что-то третье, и через пару прыжков вы снова в первом эффекте. Это и есть стиль goto: программа прыгает по коду, а чтобы понять её поведение, надо прогнать в голове все переходы.

Структурное программирование когда-то победило goto именно потому, что код стало можно читать по порядку. React добавил к этому декларативность: компонент просто описывает, как выглядит интерфейс для текущих данных. Цепочки эффектов отбирают и то и другое.

## Логика, которая живёт, пока компонент на экране

И последний подвох, о котором мало кто думает. Эффект выполняется, только пока смонтирован компонент, в котором он написан. Если важная логика спрятана в эффект, она привязана к жизненному циклу этого компонента.

```tsx
function CartBadge() {
  const items = useCartItems();
  const setTotal = useSetCartTotal();
  // плохо: сумма корзины пересчитывается, только пока виден значок
  useEffect(() => {
    setTotal(items.reduce((sum, i) => sum + i.price, 0));
  }, [items, setTotal]);
  return <span>{items.length}</span>;
}
```

Пока значок корзины виден в шапке, всё работает. А на странице оформления заказа шапка другая, значка нет, эффект не выполняется, и сумма в хранилище тихо устаревает. Такой баг ищут днями, потому что воспроизводится он только на определённых страницах. Если бы сумма вычислялась из товаров там, где она нужна, проблемы бы не было вовсе.

Кстати, переезд в стейт-менеджер сам по себе это не лечит. Если в Redux или любом другом хранилище появляется логика «когда поменялось одно, поменяй другое», это тот же самый антипаттерн, просто в другом файле.

Теперь пройдёмся по самым частым случаям, где эффект не нужен, и посмотрим, чем его заменить.

## 1. Значение можно посчитать из того, что уже есть

Самый частый и самый бессмысленный эффект. Если значение вычисляется из пропсов или другого состояния, оно не должно лежать в состоянии. Его называют производным: оно производится из других данных.

```tsx
// плохо: лишнее состояние и лишний рендер
const [fullName, setFullName] = useState('');
useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);

// хорошо: просто считаем во время рендера
const fullName = `${firstName} ${lastName}`;
```

Наш ужасный `Checkout` из начала статьи превращается вот во что:

```tsx
function Checkout({ cart, user }) {
  const items = cart.items.filter((i) => i.available);
  const total = items.reduce((sum, i) => sum + i.price * i.count, 0);
  const discount = user.isVip ? total * 0.1 : 0;
  const isValid = items.length > 0 && total - discount > 0;
  // …
}
```

Ни одного эффекта, ни одного лишнего состояния, а читается как обычная математика.

А если вычисление тяжёлое, например фильтрация списка на десять тысяч строк? Тогда его оборачивают в `useMemo`, и оно пересчитывается, только когда поменялись входные данные. А если в проекте включён React Compiler, он, как пишет документация, во многих случаях сделает это сам, и `useMemo` писать не придётся.

```tsx
const visibleTodos = useMemo(() => filterTodos(todos, tab), [todos, tab]);
```

Только не надо бросаться в другую крайность и оборачивать в `useMemo` и `useCallback` вообще всё подряд. Это преждевременная оптимизация, которую тот же Паромов разбирает как отдельный антипаттерн: код становится тяжелее, а выигрыша почти никогда нет. Мемоизируйте то, что действительно тяжело считать, и то, что профайлер показал как проблему.

## 2. Сбросить состояние, когда поменялся пропс

Классика: профиль пользователя, внутри поле комментария. Переключились на другого пользователя, а в поле остался чужой недописанный текст. Первая мысль: сбросить эффектом.

```tsx
// плохо: сначала рендер со старым комментарием, потом сброс
function Profile({ userId }) {
  const [comment, setComment] = useState('');
  useEffect(() => {
    setComment('');
  }, [userId]);
  // …
}
```

У React для этого есть встроенный механизм: ключ. Если у компонента меняется `key`, React считает его новым компонентом и создаёт с нуля, со всем состоянием внутри.

```tsx
// хорошо: другой userId значит другой компонент
<Profile userId={userId} key={userId} />
```

## 3. Поменять часть состояния, когда поменялся пропс

Чуть сложнее: список товаров и выбранный товар. Список обновился, а выбранного товара в нём больше нет. Хочется сбросить выбор эффектом. Но лучше хранить не сам объект, а его идентификатор, и вычислять выбранный товар при рендере:

```tsx
// плохо: следим за списком и чиним выбор задним числом
const [selection, setSelection] = useState(null);
useEffect(() => {
  setSelection(null);
}, [items]);

// хорошо: храним id, а сам товар находим при рендере
const [selectedId, setSelectedId] = useState(null);
const selection = items.find((item) => item.id === selectedId) ?? null;
```

Если товар пропал из списка, `selection` сам станет `null`. Никаких эффектов и никаких рассинхронов.

## 4. Код, который должен сработать из-за действия пользователя

Вот правило, которое закрывает половину всех лишних эффектов:

- Если код должен выполниться, потому что пользователь что-то сделал, ему место в обработчике события.
- Если код должен выполниться, потому что компонент появился на экране, ему место в эффекте.

Отправка формы, уведомление «Товар добавлен», запрос на сервер после клика: всё это реакция на действие. Пользователь нажал кнопку, значит, это обработчик.

```tsx
// плохо: флаг-посредник и эффект, который за ним следит
const [submitted, setSubmitted] = useState(false);
useEffect(() => {
  if (submitted) {
    post('/api/order', order);
    showToast('Заказ оформлен');
  }
}, [submitted]);

// хорошо: действие делаем там, где оно произошло
function handleSubmit() {
  post('/api/order', order);
  showToast('Заказ оформлен');
}
```

С эффектом есть ещё и тонкая ловушка: он сработает не только после нажатия, но и в любой другой момент, когда изменятся зависимости. Например, когда пользователь вернётся на страницу, и тогда уведомление покажется второй раз.

## 5. Цепочки эффектов

Это и есть та самая структура goto из начала статьи и левая колонка в демо выше. Каждое правило живёт в своём эффекте, эффекты дёргают друг друга через состояние, и никто уже не может сказать, в каком порядке что произойдёт.

Лечение то же: посчитать всё следующее состояние сразу, в том месте, где произошло событие.

```tsx
function handlePlaceCard(nextCard) {
  setCard(nextCard);
  if (!nextCard.gold) return;
  if (goldCardCount < 3) {
    setGoldCardCount(goldCardCount + 1);
    return;
  }
  setGoldCardCount(0);
  setRound(round + 1);
  if (round === 5) setIsGameOver(true);
}
```

Да, функция получилась длиннее одного эффекта. Зато вся логика в одном месте, читается сверху вниз, и React делает один рендер вместо четырёх. А часть значений, вроде `isGameOver`, вообще можно не хранить, а вычислять из `round` по правилу из первого пункта.

## 6. Сообщить родителю, что что-то поменялось

```tsx
// плохо: родитель узнаёт об изменении на рендер позже
const [isOn, setIsOn] = useState(false);
useEffect(() => {
  onChange(isOn);
}, [isOn, onChange]);
```

Здесь две проблемы. Родитель обновляется на один рендер позже, а если он передаёт `onChange`, который создаётся заново на каждом рендере, эффект будет срабатывать постоянно. Это прямой путь к бесконечному циклу.

Правильно вызывать `onChange` там же, где меняется состояние:

```tsx
function toggle() {
  const next = !isOn;
  setIsOn(next);
  onChange(next);
}
```

А ещё лучше задуматься: может, состояние вообще должно жить у родителя, а компонент просто получать `isOn` и `onChange` через пропсы? Тогда синхронизировать будет нечего.

## 7. Код, который должен выполниться один раз при старте приложения

```tsx
// плохо: в режиме разработки StrictMode запустит это дважды
useEffect(() => {
  loadDataFromLocalStorage();
  checkAuthToken();
}, []);
```

Пустой массив зависимостей не значит «один раз за всё время жизни приложения». Он значит «один раз на каждое появление компонента», а в режиме разработки React специально монтирует компоненты дважды, чтобы вы заметили такие ошибки. Код, который нужен ровно один раз, лучше вынести из компонентов: в точку входа приложения или на уровень модуля.

```tsx
if (typeof window !== 'undefined') {
  checkAuthToken();
  loadDataFromLocalStorage();
}

function App() {
  // …
}
```

## 8. Подписка на внешнее хранилище

Здесь эффект формально нужен: мы и правда синхронизируемся с внешним миром, например со статусом сети. Но для этого в React есть специальный хук, `useSyncExternalStore`, и он делает это надёжнее самописного эффекта:

```tsx
function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

function useOnlineStatus() {
  return useSyncExternalStore(subscribe, () => navigator.onLine, () => true);
}
```

## 9. Загрузка данных

Загрузка данных в эффекте работает, но в ней легко ошибиться. Самая частая ошибка: гонка запросов. Пользователь быстро напечатал «re», потом «react», и ответ на первый запрос пришёл позже второго. На экране результаты для «re», хотя в поле уже «react».

Если уж грузить в эффекте, то обязательно с очисткой, которая игнорирует устаревшие ответы:

```tsx
useEffect(() => {
  let ignore = false;
  fetchResults(query).then((json) => {
    if (!ignore) setResults(json);
  });
  return () => {
    ignore = true;
  };
}, [query]);
```

Но честнее признать, что загрузка данных уже решённая задача. TanStack Query, SWR, загрузчики в роутерах и фреймворках сами разбираются с гонками, кешем, повторными запросами и состоянием загрузки. Писать это руками в каждом компоненте не нужно.

## Откуда берутся бесконечные циклы

Отдельно про вкладку, которая тихо умирает. Почти всегда рецепт один: эффект меняет состояние, а в зависимостях лежит что-то, что на каждом рендере создаётся заново.

```tsx
// бесконечный цикл
const options = { page, sort }; // новый объект на каждом рендере
useEffect(() => {
  setData(load(options));
}, [options]);
```

Объект `options` каждый раз новый, React сравнивает зависимости по ссылке и видит изменение. Эффект срабатывает, меняет состояние, компонент рендерится заново, создаётся новый `options`, и всё по кругу.

Первое лечение, конечно, понять, нужен ли тут эффект вообще. Если нужен, зависимостями должны быть простые значения, `page` и `sort`, а не объект, который собирается при каждом рендере. И никогда не отключайте линтер зависимостей: он почти всегда прав, а `eslint-disable` над эффектом это просто отложенный баг.

## Так когда же useEffect нужен?

Когда есть настоящая внешняя система, с которой надо синхронизироваться:

- подписка на WebSocket, события `window` или `document`;
- сторонний виджет, написанный не на React: карта, редактор, график;
- таймеры и интервалы;
- аналитика «экран показан», которая срабатывает именно из-за того, что компонент появился;
- работа с DOM, которую React не делает сам: фокус, прокрутка, измерения. Для измерений, которые нужны до отрисовки, есть `useLayoutEffect`.

И у каждого такого эффекта должна быть очистка, которая отменяет то, что эффект сделал:

```tsx
useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();
  return () => connection.disconnect();
}, [roomId]);
```

Иногда внутри такого эффекта нужно прочитать свежее значение пропса, но не переподключаться из-за его изменения. Например, показать уведомление в текущей теме. Для этого в React теперь есть `useEffectEvent`: функция, обёрнутая в него, всегда видит последние пропсы и состояние, но не попадает в зависимости эффекта.

```tsx
const onConnected = useEffectEvent(() => {
  showNotification('Подключено', theme);
});

useEffect(() => {
  const connection = createConnection(roomId);
  connection.on('connected', onConnected);
  connection.connect();
  return () => connection.disconnect();
}, [roomId]); // theme здесь не нужен
```

## Чек-лист перед тем, как написать useEffect

1. С какой внешней системой я синхронизируюсь? Если ни с какой, эффект не нужен.
2. Есть ли в эффекте что-то, кроме `setState`? Если нет, эффект не нужен.
3. Можно ли посчитать это значение из того, что уже есть? Тогда считаем при рендере и не храним копию.
4. Это реакция на действие пользователя? Тогда это обработчик события.
5. Нужно сбросить всё состояние при смене пропса? Тогда `key`.
6. Это подписка на внешнее хранилище? Тогда `useSyncExternalStore`.
7. Это загрузка данных? Тогда библиотека или хотя бы очистка от гонок.
8. Будет ли логика работать, если этот компонент не смонтирован? Если нет, ей не место в эффекте.
9. Если эффект всё-таки нужен, есть ли у него очистка и честный список зависимостей без `eslint-disable`?

## Подведём итоги

`useEffect` не место для бизнес-логики, вычислений и реакции на клики. Это узкий инструмент для синхронизации с внешним миром. Каждый раз, когда эффект просто кладёт что-то в состояние, вы получаете лишний рендер, возможный мерцающий кадр и ещё одно звено в цепочке, которую следующему разработчику придётся распутывать.

Хорошая новость в том, что почти любой лишний эффект удаляется механически: значение считаем при рендере, действие делаем в обработчике, сброс делаем ключом. Код от этого становится короче, быстрее и, главное, понятнее.
